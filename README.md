# Moldovagaz — contoare de gaz LoRaWAN

Next.js 16 (App Router, Cache Components) + MongoDB. Arată contoarele de gaz Moldovagaz din SCADA (≈69.000, cele 10 filiale) într-un tabel, pe hartă și într-un tablou de grafice, cu totaluri, filtre și sortare **instant**, iar pentru fiecare contor istoricul **Volume (m³)**.

## Sursele de date

| Sursă | Ce aduce |
|---|---|
| **SCADA** (ThingsBoard, `iiot.scada.md` / `192.168.77.24:8080`) | **lista contoarelor** (dispozitivele celor 10 clienți de gaz, inclusiv `Defectate_*`: vezi [lib/meter-scope.ts](lib/meter-scope.ts)), valorile curente (`Volume_m3_Total`, `Volume_m3_Total_ts`, **coordonate** `latitude` / `longitude`, RSSI/SNR, baterie, consumuri…), atributele și **istoricul** |
| `getmgdb` (`http://192.168.77.11:3880/getmgdb`) | facturarea: **filiala (FIL)**, cont (ACCT_ID), **număr radio**, adresă, consumator, secție, controlor… |

**Legătura facturare ↔ dispozitiv:** `NUM_RADIO` (8 cifre) = seria din numele dispozitivului (`S2154_00070948_2022` → `00070948`). **Filiala:** codul `FIL` din facturare (01 Chișinău, 05 Comrat, 10 Edineț, 11 Cahul, 20 Orhei, 27 Taraclia, 31 Florești, 33 Cimișlia, 35 Ștefan Vodă, 36 Ialoveni); contoarele fără facturare primesc filiala clientului lor din SCADA (fiecare filială are un client: `ComratGaz_DashGroup`, `OrheiGaz_DashGroup`…). Cheile LoRaWAN (APPKEY / NWKSKEY / APPSKEY) **nu** se copiază niciodată în aplicație.

## Trei pagini

| Pagină | Adresă | Ce arată |
|---|---|---|
| **Contoare** (principala) | `/` | contoarele din SCADA **combinate** cu facturarea: volum, coordonate, semnal, baterie, stare, cu hartă și istoric |
| **Dispozitive LoRaWAN** | `/lorawan` | **doar** datele din lorawandb (`http://192.168.77.11:3880/lorawandb`), exact cum le dă sursa: nume, profil, etichetă, client, data creării (+ serie / model / an extrase din nume, serii repetate). Nu are volum, coordonate sau semnal; lista poate fi în urma SCADA |
| **Facturare** | `/facturare` | **doar** datele din getmgdb: consumator, adresă, filială, număr radio, serie contor, cont, secție, cod abonat, data actualizării… — toate rândurile (și cele fără contor în SCADA) |

Paginile pe sursă au aceleași instrumente ca pagina principală: căutare cu mai multe cuvinte, filtru sub fiecare antet de coloană și „Mai multe filtre” pentru restul câmpurilor, filtre active ca etichete cu ✕ (în URL), totaluri, sortare pe orice coloană, grafice (click pe bară filtrează, glisarea alege un interval de timp), detalii pe rând cu toate câmpurile și export CSV (fără datele personale). Coloanele sunt definite în [lib/source-schemas.ts](lib/source-schemas.ts); câmpurile necunoscute din getmgdb apar singure ca coloane text în detalii. Din detalii poți sări la pagina principală (`/?name=…` sau `/?q=<număr radio>`).

## Sincronizarea

Înainte de valorile din SCADA, sincronizarea salvează și **rândurile brute** din lorawandb și getmgdb în colecțiile `src_lorawan` și `src_billing` ([lib/source-sync.ts](lib/source-sync.ts)): paginile pe sursă rămân la zi chiar dacă SCADA nu răspunde. Se scriu doar rândurile schimbate (hash pe conținut); din lorawandb se păstrează doar câmpurile de identificare (**fără** `deviceData` și chei LoRaWAN). Lista contoarelor din aplicație NU vine din lorawandb, ci din SCADA. Serverul ține lista în memorie (gzip, ETag = amprenta datelor), iar browserul o păstrează în IndexedDB și o verifică la 60 s (304 când nu s-a schimbat nimic).

`scripts/sync-meters.ts` (pm2: `<nume>-sync`, o dată pe oră, la minutul 0): citește facturarea (getmgdb), lista contoarelor din SCADA (pe client, pagini de 1000) și valorile curente (loturi de 500), cu o **pauză între cereri** (`TB_PAUSE_MS`, implicit 150 ms) ca încărcarea serverului SCADA să rămână mică. Combină totul și scrie în colecția `meters` **doar contoarele ale căror date s-au schimbat** (hash pe conținut). Contoarele care nu mai sunt în SCADA se șterg (cu plasă de siguranță dacă dispar prea multe deodată). **Doar citire** din SCADA: clientul refuză orice apel în afară de login, interogări și citiri de liste / serii. Fără `TB_URL` nu pleacă nicio cerere.

```bash
npm run sync:meters                       # sincronizare completă
npm run sync:meters -- --dry              # doar citește și combină; afișează statistici (nu scrie nimic)
npm run sync:meters -- --dry --out f.json # la fel, + salvează documentele într-un fișier
npm run sync:meters -- --load f.json      # scrie documentele din fișier (fără rețea) — încărcare inițială
npm run sync:meters -- --patch-geo        # completează coordonatele pe documentele existente, din atributele lor (fără rețea)
npm run sync:sources                      # doar rândurile brute din lorawandb + getmgdb → `src_lorawan` / `src_billing` (fără SCADA)
npm run sync:sources -- --dry             # le citește și numără, fără să scrie nimic
npm run check                             # verifică filtrele, agregările, actualizările pe loc și combinarea (date sintetice)
```

## Cum e făcut să meargă instant

Același model ca „tasks” din StefanPWA, adaptat la rânduri care se modifică pe loc:

1. **Server (memorie)** — `lib/services/meter-dataset.ts`. Lista, coloanar, în memoria procesului. La fiecare cerere se verifică o *amprentă* ieftină din Mongo (total + ultimul `updatedAt`); dacă s-a schimbat, se aduc **doar** documentele modificate și se suprascriu rândurile (fiecare modificare primește un `seq`). Gzip-ul se face o dată și se memorează pe versiune. `ETag = generație.seq` → `304` fără corp.
2. **Browser, IndexedDB** — vectorii tipizați se salvează ca atare; la deschidere lista apare din cache local, fără `JSON.parse`.
3. **Browser, memorie** — obiectul `MeterStore` rămâne cât timp fila e deschisă.
4. **Sincronizare incrementală** — `/api/meters/delta?after=<seq>` întoarce doar contoarele modificate (zero rânduri = câteva zeci de octeți). „Live” = o întrebare la 30 s cât timp fila e vizibilă.
5. **Virtualizare** — în DOM stau ~20 de rânduri, indiferent de număr; filtrarea / sortarea rulează într-o trecere peste vectori tipizați (câțiva ms).
6. Prima pictare vine din HTML (primele 40 de rânduri) și, dacă browserul are deja versiunea curentă, **nu se face nicio cerere**.
7. **Istoricul** unui contor nu intră în listă: se citește din ThingsBoard doar când deschizi contorul (`/api/meters/<id>/history`, doar citire, 60 s în memorie).

## Filtre și grafice

- **Filtre** (toate optimiste, combinabile; între filtre diferite ȘI, între valorile aceluiași filtru SAU): căutare liberă (nume contor, devEUI, număr radio, cont, adresă, consumator), **filială**, oraș, profil, stare (**activ 24 h / avertizare 1–7 zile / critic peste 7 zile**, ca în SCADA, după ultima citire; alerte = baterie slabă sau inactiv în SCADA; „raportat offline de contor” e câmpul trimis de contor în propriul mesaj, nu starea conexiunii; buton / magnet), perioada ultimei citiri (presetată sau personalizată) și, în „Mai multe filtre”: aplicație, concentrator, tip mesaj, frecvență, fPort, model, an / cod lot, facturare, intervale pentru **Volume (m³)**, consum zilnic, baterie, RSSI, SNR și fCnt. Filtrele active apar ca etichete cu ✕ și se păstrează în URL.
- **Grafice** (fila „Grafice”, același filtru ca tabelul): contoare după ultima citire, stare și alerte, contoare și **volum pe filială**, orașe, profile, aplicații, concentratoare, tipuri de mesaj, histograme pentru Volume / consum zilnic / baterie / RSSI / SNR, harta RSSI × SNR, frecvențe, fPort, model, an, ora și ziua ultimei citiri, prospețimea citirilor și topul consumurilor. Click pe o bară filtrează, glisarea alege un interval, contextul „toate” rămâne în gri, iar „Tabel” de pe fiecare card arată datele.
- **Hartă** (fila „Hartă”, aceleași filtre ca tabelul): toate contoarele cu coordonate (latitude / longitude din atributele ThingsBoard, ~64% dintre contoare), colorate după stare, semnal, vechimea citirii sau baterie. Punctele se desenează pe un singur canvas și se grupează în bule (O(n), ~2 ms la 44.000 de puncte, recalculat doar la schimbarea zoom-ului): zoom și deplasare la 60 fps. Click pe o bulă = zoom, click pe un punct = popup cu datele contorului și butoane Google Maps / Waze / Apple Hărți. Harta de bază: dale OpenStreetMap (browserele utilizatorilor le cer direct de la tile.openstreetmap.org; pentru trafic mare folosește un furnizor de dale propriu).
- **Detaliu contor** (click pe rând): **harta proprie a contorului** cu butoane de navigare (Google Maps, Waze, Apple Hărți, OpenStreetMap), Volume (m³) cu consum pe zi / oră din `Volume_m3_Total_ts`, facturare completă, ThingsBoard, ultima telemetrie, atribute, JSON.

## Consum nemăsurat (indiciu de gaz care trece pe lângă contor)

Pagina `/control`: contoare care **noaptea nu înregistrează consum** (sau foarte puțin; implicit 00:00–06:00, ora Moldovei, dar **intervalul se alege în pagină**, inclusiv peste miezul nopții, ex. 22:00 → 04:00), deși **ziua consumă** și **temperatura din jurul contorului nu scade** (încălzirea merge). Toți parametrii se pot edita în pagină (intervalul nopții, **scăderea maximă a temperaturii noaptea față de zi** — „volumul scade noaptea, dar temperatura rămâne ca ziua” —, nopți analizate, consum maxim de noapte, consum minim de zi, temperatură minimă — minima din noapte sau media pe zi —, câte nopți trebuie să se potrivească); lista se recalculează instant și rămâne în URL.

- **Date:** doar din baza noastră, fără cereri suplimentare către SCADA. Sincronizarea de la fiecare oră salvează, pentru fiecare contor cu citire nouă, un punct (momentul citirii, volumul, temperatura din același mesaj) în `meter_readings` ([lib/meter-readings.ts](lib/meter-readings.ts)); pentru zilele de dinainte se folosește arhiva veche de volum `meter_history` (fără temperatură), **doar seria pe oră `Volume_m3_Total_ts`** (ora la care contorul a CITIT volumul, nu ora sosirii mesajului în SCADA; ora citirii e și în `meter_readings`).
- **Calcul:** [lib/night-analysis.ts](lib/night-analysis.ts). Contorul trimite la 4–6 ore, deci volumul se estimează prin interpolare liniară între citirile vecine, doar dacă ele sunt la cel mult 8 ore una de alta; altfel ora e „necunoscută” (noaptea ignorată, nu 0). Pentru fiecare contor se păstrează **profilul pe ore** al ultimelor 30 de zile (consum în 0,001 m³ și temperatură minimă în 0,5 °C, ~2,2 KB / contor, în `meter_nights`, [lib/night-job.ts](lib/night-job.ts)), recalculat o dată pe zi la sfârșitul sincronizării sau la cerere: `npm run analyze:nights`. Intervalul ales, pragurile și numărul de nopți se aplică **la cerere**, pe profilul din memoria serverului, fără alocări (calea rapidă `countFromProfile`, identică cu cea pe rânduri, verificată pe mii de combinații); lista se încarcă la pornirea serverului și se reîncarcă în fundal după fiecare analiză. Măsurat local la 69.000 de contoare: ~15 ms la fiecare modificare de parametru, prima cerere 63 ms (înainte 80 ms și 578 ms). „Ziua” = restul celor 24 de ore dintre începutul unei nopți și începutul următoarei. Ține cont de schimbarea orei (zile de 23 / 25 h).
- **Limite:** e un **indiciu**, nu o dovadă. Locuințe cu alt mod de încălzire, contoare montate în exterior (temperatura urmărește vremea) sau citiri prea rare pot da potriviri false sau lipsă. Modelele fără temperatură (S3010) nu pot fi analizate cu condiția de temperatură. Temperaturile se adună de la prima sincronizare după activare: după 7 zile sunt 7 nopți, după 14 zile 14.

## Integrare: mesaje direct de la LoRaWAN / antene

API-ul `POST /api/integration` (pagina `/integration`) primește mesaje de contor **direct** de la rețeaua LoRaWAN / antene, fără SCADA, în forma documentului unui contor: `{ id?, tb: { name, type, customerId, … }, bill?, attrs?, tel: { <cheie>: { t, v } } }` (un obiect sau o listă, cel mult 8 MB, opțional `Content-Encoding: gzip`). Contorul se identifică prin `id` (UUID), `tb.name` sau `attrs.devEUI`. Autentificare: `Authorization: Bearer <INTEGRATION_TOKEN>` (sau `X-Integration-Token`); `INTEGRATION_TOKEN` are minimum 24 de caractere, altfel integrarea e dezactivată. **Nu există blocare pe adresă**: un token greșit primește 401 cu motivul (lipsește antetul, format greșit, lungime diferită, token greșit), iar un token corect trece oricând.

**Garanția de livrare** ([lib/services/integration.ts](lib/services/integration.ts)): un răspuns **200** înseamnă că mesajele sunt salvate **durabil** într-o „cutie de intrare” (`integration_inbox`, scriere cu jurnal) și că vor fi aplicate pe contoare în câteva secunde. Un proces de fundal (pornit din [instrumentation.ts](instrumentation.ts), deci și după o repornire) golește cutia în pachete de 1000: îmbină mesajele aceluiași contor în ordinea sosirii, le aplică pe `meters` cu **aceeași derivare ca la sincronizarea din SCADA** (volum, stare, filială, căutare…), adaugă citirea în istoricul propriu (`meter_readings`, de unde se calculează „Consum nemăsurat”) și abia apoi șterge mesajele din cutie. Aplicarea e **idempotentă** (telemetria cu momentul cel mai nou câștigă, un mesaj mai vechi sosit târziu nu suprascrie nimic, același conținut nu se rescrie), deci o reaplicare după o cădere nu are efecte duble. Eroare de bază de date ⇒ pauză cu întârziere crescătoare, mesajele rămân în cutie. Mesajele care nu se pot aplica merg în `integration_dead` (30 de zile). Cutia plină (`INTEGRATION_MAX_INBOX`, implicit 500.000) ⇒ **503 + Retry-After**, nu pierdere. **Expeditorul trebuie să reîncerce** orice răspuns diferit de 200 (sau lipsa răspunsului): reîncercarea e sigură.

**Orice se poate trimite, fără eroare**: ce nu se potrivește cu formatul de contor (alt format, contor necunoscut, text care nu e JSON) se **păstrează pentru procesare ulterioară** în `integration_raw` (cu motivul, 90 de zile) și se răspunde tot 200; se reia automat la pornire și la 10 minute (de ex. după ce apare contorul) sau cu butonul „Reia acum” din pagina `/integration`. Răspunsuri: 200 `{received, accepted, kept, reasons?}` (accepted = se aplică pe contoare, kept = păstrat) · 401 token (cu motivul) · 413 mai mare de 8 MB · 503 ocupat / dezactivat. Cheile de rețea LoRaWAN (APPKEY, NWKSKEY…) nu se păstrează niciodată. Contoarele ale căror date au venit prin integrare și sunt la fel de noi ca cele din SCADA nu sunt suprascrise de sincronizarea din SCADA.

**Formatul uplink-urilor LoRaWAN** ([lib/integration-uplink.ts](lib/integration-uplink.ts)): pe lângă documentul de contor, API-ul înțelege direct uplink-urile brute ale serverului LoRaWAN (ChirpStack, decodor Jooby: `devEUI`, `deviceName`, `rxInfo`, `txInfo`, `fCnt`, `object.decoded[]`). Contorul se găsește după **`devEUI`** (cel mai sigur), apoi după nume (fără prefixul S / SN, deci `2154_00073058_2022` ≙ `S2154_00073058_2022`, doar dacă e unic). Se extrag: semnal (RSSI / SNR), frecvență, concentrator, `fCnt`, `fPort`, aplicație, `decodeTime` (momentul mesajului), starea din cadrul `LastEventSeq` (offline, magnet, buton, baterie slabă), baterie și temperatură din `DeviceStatus`, `ieType` = tipul ultimului cadru. **Volumul total** (m³) se calculează din contorul de impulsuri (`CurrentDataMul` / `CurrentData`): litri = `Instalation_Litres` + (impulsuri − `ModuleInitialValue`) × 10 (1 impuls = 10 L); formula e verificată pe date reale (0,28 · 8.612,099 · 0,063 · 2.209,289 m³) și volumul doar crește. Un uplink **vechi** (reluare) — `fCnt` mai mic, fără impulsuri în plus, valoare cunoscută din ultimele 48 h — nu schimbă nimic; un contor repornit (fCnt mai mic dar impulsuri mai multe) se acceptă. Pagina `/integration` arată de la ce contoare vin datele (cu numărul de mesaje) și ce s-a păstrat, grupat pe dispozitiv, cu contorul cu care se potrivește. Nu se folosesc încă cadrele orare `HoursDataMul` (ceasul contorului e uneori greșit).

**Antene pe hartă** ([lib/services/gateways.ts](lib/services/gateways.ts), [app/components/GatewayLayer.tsx](app/components/GatewayLayer.tsx)): din `rxInfo` al fiecărui uplink se rețin antenele (gateway-uri) care au auzit mesajul: colecția `integration_gateways` (nume, poziție, mesaje, ultimele 20 de cereri) și `integration_gw_dev` (perechea antenă × contor: mesaje, RSSI / SNR). Pe fila **Hartă** apar antenele (verde = a auzit ceva în ultima oră, galben = sub 24 h, roșu = offline); click pe o antenă arată eficiența ei (contoare auzite, câte are ca antenă principală, câte aude doar ea, RSSI / SNR mediu), ultimele cereri, cel mai apropiat și cel mai îndepărtat contor (distanța din coordonate) și trasează linii spre contoarele auzite; click pe un contor arată antenele care îl aud (cea cu semnalul cel mai bun = principală). Ora este ora mesajului din rețea (`decodeTime`), nu ceasul antenei (unele antene îl au greșit cu zile); antenele cu poziția (0, 0) sau în afara Moldovei se numără, dar nu se pun pe hartă. API: `GET /api/integration/gateways` (listă), `?id=<antenă>` (detalii), `?device=<contor>` (antenele unui contor). Se umple doar din mesajele primite după punerea în funcțiune (și din cele păstrate, la reluare).

**Verificarea continuității** ([lib/integration-counter.ts](lib/integration-counter.ts), [lib/services/counters.ts](lib/services/counters.ts)): dacă expeditorul pune un număr crescător pe fiecare mesaj (`msg_counter`, sau `counter` / `cnt` / `seq`, la rădăcina mesajului sau în `object` / `data`; majusculele, „_” și „-” nu contează; opțional `stream` cu numele expeditorului când sunt mai mulți), pagina `/integration` arată câte numere trebuiau să vină, câte au venit, ce numere **lipsesc** și **peste câte a sărit** (cu ora observării), plus cele sosite târziu (altă ordine) și duplicatele (reîncercări). Numărătoarea se face la primire, după salvarea durabilă și înainte de răspunsul 200, deci un mesaj refuzat (503) nu se numără până nu e reîncercat. Stare în `integration_counters`; „Test nou” o șterge. API: `GET /api/integration/counters`, `POST` cu `{ "reset": "all" }`.

Instrument de încărcare și verificare: `npm run bench:integration -- load | burst | verify | auth` (doar pe o bază de TEST). Rezultate măsurate local (un singur proces Node, MongoDB local): ritm de 20 cereri/s → latență p50 20 ms / p99 22 ms; vârf de 250 cereri simultane → ~1.200 cereri/s, p99 430 ms; 80.000 de mesaje în pachete de 200 primite într-o secundă și aplicate în 3 s; oprire brutală a serverului în mijlocul unui vârf de 12.000 de cereri ⇒ după repornire toate mesajele confirmate sunt aplicate (0 pierdute).

**Pânză de widgeturi** (pagina `/integration`, [app/components/Board.tsx](app/components/Board.tsx), [Widget.tsx](app/components/Widget.tsx)): fiecare card se **trage** de mânerul ⠿ din colț (sau cu săgețile, de la tastatură) ca să-i schimbi locul, se **închide** cu ×, se **redimensionează** trăgând marginea dreaptă (lățime), cea de jos (înălțime) sau colțul (dublu-click = mărimea inițială; un widget mai îngust lasă loc altuia alături) și se **mărește pe tot ecranul** cu „Mărește” (Esc = înapoi). Butonul „Widgeturi” listează toate cardurile cu bife pentru ce e vizibil și „Aranjare implicită”. Ordinea, ce e ascuns și mărimile se rețin în browser. Rândul cu starea („Primite / secundă”…) rămâne fix: arată dacă integrarea funcționează. Listele mari (contoare care trimit, date păstrate) sunt ferestre derulante, cu pagini aduse la nevoie. Scrollbar-urile sunt subțiri, în culorile temei.

**Antene în Grafice** ([app/components/GatewayCharts.tsx](app/components/GatewayCharts.tsx), [lib/gateway-stats.ts](lib/gateway-stats.ts)): în fila „Grafice”, la sfârșit, secțiunea „Antene: eficiență pe perioadă” cu filtre PROPRII (separate de cele ale contoarelor): perioadă (Azi / 7 / 30 / 90 de zile sau interval ales, până la 120 de zile), stare antenă (activă / lentă / offline), căutare după nume, minim de contoare auzite și sortare. Arată pentru fiecare antenă contoare auzite, mesaje, mesaje pe contor, RSSI / SNR, zile active și câte contoare aude doar ea; seria pe zile (mesaje, contoare auzite pe zi, antene active); click pe o antenă = seria ei. **Click pe o antenă** (în tabel sau în graficul „Contoare auzite”) deschide un popup ca panoul de pe hartă ([GatewayPopup.tsx](app/components/GatewayPopup.tsx)): stare și ultimul mesaj, contoare auzite / pentru care e principală / auzite doar de ea, RSSI / SNR, cel mai apropiat și cel mai îndepărtat contor, ultimele cereri, o hartă mică cu antena și TOATE contoarele cu care comunică (colorate după semnal) și lista completă a contoarelor (căutare, sortare); click pe un contor deschide detaliile lui. „Arată în grafic” afișează seria pe zile a acelei antene. Datele pe zile (`integration_gw_day`: mesaje, sume RSSI / SNR, contoare-zile; ziua = ziua UTC; ținute 400 de zile) se strâng din mesajele primite DUPĂ punerea în funcțiune, deci istoricul se umple de acum înainte. „Contoare auzite” = contoarele cărora antena le-a auzit ultimul mesaj în perioadă (din perechile antenă × contor). API: `GET /api/integration/gateways?stats=1&from=&to=&state=&q=&min=&sort=&gw=`.

**Săgeți contor → antenă**: când alegi un contor pe hartă, de la contor pornesc linii cu săgeată spre fiecare antenă care l-a auzit (cea principală, cu semnalul cel mai bun, e mai groasă și cu săgeata mai mare; culoarea arată dacă antena e activă / lentă / offline), iar panoul „Antene” le listează cu distanță, RSSI, SNR și mesaje. Aceeași listă, cu săgeți, e și în panoul de detalii al contorului din tabel ([app/components/MeterAntennas.tsx](app/components/MeterAntennas.tsx)). Cardurile „instrucțiuni de trimitere” și „Verifică un mesaj” din `/integration` se pot închide (alegerea se reține în browser).

**Coloane ca în lista din SCADA** ([app/components/meter-columns.ts](app/components/meter-columns.ts)): butonul „Coloane” alege ce se vede în tabel (alegerea se reține în browser; „Implicit” / „Toate”). În plus față de coloanele de bază: SPID, Cont personal, Contor SN, Litri la instalare, Aragaz, Cazan, Încălzire, Data calibrării, Adresă (stradă), Bloc / casă, Apartament, Latitudine, Longitudine. Fiecare are filtru în antet (text „conține”, interval, da / nu, interval de date) și apare în URL și în etichetele filtrelor active; sincronizarea citește în plus atributele `Incalzire` și `Data_Calibrarii`. Punctul „Activ” are culoarea treptei de activitate (verde sub 24 h, galben 1–7 zile, roșu peste 7 zile; contor marcat inactiv ⇒ roșu), iar „Activitate” arată `<1 zi` / `1<7 zile` / `>7 zile`, ca în SCADA. Exportul CSV nu include adresa și identificatorii consumatorului.

**Contoarele „Defectate_*”** sunt în aplicație (trimit mesaje); filtrul „Grup Defectate în SCADA” le arată separat sau le ascunde.

**Date păstrate** (pagina `/integration`, cardul „Toate datele păstrate”): lista completă a mesajelor păstrate, ca fereastră derulantă (în DOM doar rândurile vizibile; pagini de 100, aduse la nevoie și reținute), cu filtru pe motiv, căutare după dispozitiv / devEUI / aplicație și conținutul mesajului la click. „Curăță…” șterge tot sau doar un motiv, dar ÎNTÂI reia și aplică ce se potrivește acum cu un contor și șterge doar ce era păstrat înainte de apăsare. Reluarea e automată (la 5 s după pornire și în fiecare minut). API: `GET /api/integration/kept` (pagină, `?reasons=1`, `?id=`), `POST` cu `{ "action": "clear", "reason"?: "…" }`.

**Activitate ca în SCADA** (tabelul de contoare): „Ultima citire” = momentul în care contorul a CITIT volumul (`Volume_m3_Total_ts`, cu secunde), nu momentul sosirii în SCADA (`Volume_m3_Total`); dacă `Volume_m3_Total_ts` lipsește se folosește cel de-al doilea. Două coloane, cu filtru în antet: **Activ** (atributul `active` din SCADA: verde = true, roșu = false, gri = lipsește) și **Activitate** (sub 24 h = verde, 1–7 zile = galben, peste 7 zile = roșu, fără citire = gri). În „Mai multe filtre” mai sunt `lastActivityTime` (ultima activitate văzută de platformă) și `inactivityAlarmTime` (momentul alarmei de inactivitate), ca intervale de dată, plus „cu / fără alarmă”; toate se pot combina și apar în URL și în export CSV. Câmpul `offline` din mesajul contorului nu se mai afișează și nu se filtrează (nu spune nimic despre activitate). Integrarea scrie `Volume_m3_Total_ts` odată cu volumul din impulsuri, ca o citire nouă primită direct să nu rămână în urma uneia vechi din SCADA.

**Filtre de temperatură în „Consum nemăsurat”** (`/control`): temperatura minimă (se poate lăsa goală = fără minim), temperatura **maximă** (goală = fără limită), „Doar contoare cu temperatură” (arată doar contoarele / nopțile cu temperatură măsurată, indiferent de valoare; cartea „Cu temperatură” arată câte sunt) și „Temperatura rămâne ca ziua”. Se compară minima din noapte sau media pe zi, la alegere. Condițiile sunt în adresa paginii, deci o căutare se poate trimite mai departe.

**Consum pe perioadă** (cartea „Consum” de sus): suma consumului raportat de contoare în **perioada curentă**, la alegere „Azi” (ziua calendaristică, `dailyConsumption`) sau „Luna aceasta” (`monthlyConsumption`), doar pentru contoarele filtrate; se adună doar contoarele al căror consum e înscris în SCADA pentru ziua / luna de acum (restul au valori vechi și ar falsifica totalul), iar cartea arată și câte contoare au raportat din câte sunt filtrate. Înlocuiește vechea „sumă a ultimelor citiri de volum”, care aduna volume cumulate citite în zile diferite și nu însemna nimic. Alegerea se reține în browser.

## Raportul de citiri către facturare (Oracle)

Pagina **Rapoarte**: alegi **data și ora** (ex. 01/12/2026 07:00, ora Moldovei; nu în viitor) și dacă doar contoarele legate de facturare; **Previzualizează** arată primele rânduri și o estimare, **Generează fișierul** scrie CSV-ul pe server în fundal (un singur raport odată, cu progres).

- **Conținut**: câte **o linie pe contor**, cu **cea mai recentă citire făcută până la momentul ales**, și doar trei câmpuri, separate cu `;`: `num_radio` (seria radiomodulului: NUM_RADIO din facturare, altfel cele 8 cifre din numele dispozitivului), `indicatia_m3` (volumul total, 3 zecimale cu punct) și `data_citire` (momentul real al citirii, `ZZ/LL/AAAA HH:MM:SS`, ora Moldovei). Contoarele fără nicio citire până atunci sau fără serie de radiomodul nu apar.
- **Locul fișierelor**: `REPORT_OUT_DIR` (director local sau montat din rețea); implicit `reports/` lângă aplicație. Fișierul (`citiri_<AAAA-LL-ZZ_HHMM>_<generat>.csv`) se scrie întâi ca `.part` și se redenumește abia când e complet, deci cine urmărește directorul vede doar fișiere întregi; lângă el e `.sha256` (suma de control).
- **Automat**: aplicația pm2 `<nume>-report` rulează pe **1 ale lunii la 07:00** (ora serverului) și generează raportul pentru **1 ale lunii, ora 07:00** (ultima citire a fiecărui contor până atunci; doar contoare legate de facturare; schimbabil cu `REPORT_ONLY_BILLED` / `REPORT_HOUR`). Dacă serverul a fost oprit în ziua 1, recuperează în primele 5 zile și nu repetă un raport deja făcut. Manual: `npm run report:monthly -- --force`.
- **Sursa citirilor**: istoricul propriu de citiri (`meter_readings`), arhiva veche de volum (`meter_history`) și ultima citire din documentul contorului, combinate, fără dubluri. Ora citirii e cea la care contorul a măsurat volumul (`Volume_m3_Total_ts`), nu momentul sosirii în platformă. Nimic nu se citește din SCADA la generare.

## Pozele contoarelor

În SCADA fiecare contor poate avea atributul `image` (poza de la montaj, JPEG ca text base64, 1,5–3,5 MB). Nu le păstrăm așa: [scripts/pull-photos.ts](scripts/pull-photos.ts) ([lib/photo-job.ts](lib/photo-job.ts)) le citește din SCADA (**doar citire**, un contor pe cerere, doar cheia `image`), le decodează, le micșorează cu `sharp` (cel mult 1600 px pe latura lungă, orientarea din EXIF aplicată, **fără metadate, deci fără locația din poză**) și le scrie ca fișiere pe disc: `<PHOTO_DIR>/<primele 2 caractere ale id-ului>/<id>.jpg` și `<id>_t.jpg` (miniatură de 240 px). Originalele nu se păstrează (~150 GB). În Mongo, colecția `meter_photos` ține doar starea fiecărui contor (`ok` / `none` / `err`).

- **Afișare:** în detaliile fiecărui contor poza apare sus (click = popup cu zoom: rotiță spre cursor, butoane +/−, dublu-click, tragere pentru deplasare, ciupire pe tactil, taste + − 0 și săgeți, Esc); fără poză, nu ocupă loc. Ruta: `GET /api/meters/<id>/photo` (`?size=thumb` = miniatura), doar autentificat.
- **Pornire:** aplicația pm2 `<nume>-photos` (zilnic la 22:00 și o dată la creare) pornește **doar cu `PHOTO_PULL=1`** în `.env.local`; sau manual `npm run photos:pull -- --now [--limit 200] [--refresh]`. Prima rulare le ia pe toate; apoi doar contoarele noi, cele fără poză (reverificate o dată la 7 zile) și cele cu eroare (după 10 min, de cel mult 5 ori).
- **Reluabil și blând cu SCADA:** se poate opri oricând (pm2 stop / Ctrl+C) și continuă de unde a rămas; `PHOTO_CONCURRENCY` cereri deodată (3), `PHOTO_PAUSE_MS` între ele (150); se oprește singur dacă pe disc rămân sub `PHOTO_MIN_FREE_GB` (3) GB sau dacă SCADA nu răspunde 5 minute la rând.
- **Loc și mărime:** `PHOTO_DIR` (implicit `photos/` lângă aplicație; poate fi un alt disc), `PHOTO_MAX_PX` (1600, ca să se poată mări la zoom). Estimat ~7 GB pentru toate contoarele (la 1000 px erau ~3,5 GB); pozele păstrate la o rezoluție mai mică decât cea cerută se refac singure, o dată. Pozele se pot reface oricând din SCADA.

## Ecranul instalatorului (/instalator)

Copia aplicației din SCADA pe care o folosesc instalatorii (dashboardul **<Filială>_Gaz_App**, starea **<Filială>_Gaz_Meter_App**; citit din configurația SCADA, doar citire), ca să nu li se pară nimic nou: aceeași bară verde (`#01695c`), fonturi Roboto, aceleași 6 widgeturi, câmpuri, etichete, butoane, culori și mesaje (română / engleză / rusă). Pagina nu are bara de sus a aplicației noastre (meniul ⋮ are «Moldovagaz» și «Sign out»).

- **Select Device** (`FilterDevices`, păstrat per utilizator; «Anulează Ultima Comandă» / «Salvează»), **Device admin table** («Nume Entitate», `active` = cerc verde / galben / roșu după ultima citire, `ActiveTime` = «<1 day» / «1<7 days» / «>7 days», `Volume_m3_Total`, `Instalation_Litres`, `Volume_Liters`, `ModuleinitialValue`, `lastActivityTime`; căutare, alegere de coloane, paginare; pe telefon acțiunile rândului sunt în ⋮), **Meter Update** (`ContorNr`, `Instalation_Litres`, `latitude` / `longitude`, `image`, `Aragaz`, `Cazan`, `Incalzire`, `Module Calibration`, `Localitate`, `Comments`), **Instalation Photo** (click = popup cu zoom), **Installation foto** (doar pe ecran lat) și **Module Location** (hartă OpenStreetMap cu locul contorului).
- **«Salvează» se activează doar când formularul e valid și modificat**, ca în SCADA: `ContorNr`, `Instalation_Litres`, locația și poza sunt obligatorii. Locația și poza se salvează imediat, din butoanele lor.
- **Camera** (poza: «Refă» / «Confirmă», până la 2048 px) și **scanarea QR** (cadru, zoom, lanternă; «Îndreaptă camera spre QR / Наведите камеру на QR»), plus **GPS**, merg doar pe HTTPS. Codul QR se recunoaște ca în SCADA (`:S2154.…:`, `2514.…!N…`, `:3010.…:`, `:3020.…:`); după o scanare reușită contorul se alege, filtrul se pune pe numele lui, codul se salvează și locația se salvează automat.
- **Datele se salvează DOAR la noi**, nu în SCADA (rămâne strict citire): colecția `installer_data` (un document per contor, cu cine și când a salvat) și poza ca fișier în `<PHOTO_DIR>/installer/…` (micșorată, fără locația din poză); poza instalatorului are prioritate față de cea din SCADA în `/api/meters/<id>/photo`. `Permissions-Policy` din [next.config.ts](next.config.ts) permite camera și GPS-ul doar aplicației însăși.
- «Localitate»: la Orhei lista din SCADA (Orhei, Soldanesti, Rezina, Telenesti); la celelalte filiale, valorile folosite la cel puțin 20 de contoare ale filialei. `Volume_Liters` și `inactivityTimeout` se citesc acum la sincronizare (apar după următoarea rulare orară).

- **Tabelul e instant, ca pagina Contoare:** lista contoarelor (doar zona utilizatorului) stă în memoria serverului, coloanar și mică (`lib/services/installer-store.ts`), se descarcă o dată în browser (`/api/installer/dataset`, ETag ⇒ 304 la redeschidere) și căutarea (nume / ContorNr), sortarea și paginarea (10 … 1000 / All, cu rânduri desenate doar cât se văd) sunt locale. Se pune la zi singură cu rândurile schimbate (`?since=`) și după fiecare salvare; ce introduc instalatorii (`/api/installer/edits`) suprascrie valorile din SCADA în tabel.

## Utilizatori și drepturi (/utilizatori)

- **Administrator** = contul cu rolul `super_admin` (se creează cu `npm run seed:user -- email parola "Nume" super_admin`): vede tot și are pagina **Utilizatori**, unde creează conturi, schimbă parole, dezactivează / șterge. Nu-și poate scoate singur drepturile și mereu rămâne cel puțin un administrator activ.
- **Utilizatorii limitați** (orice alt cont) văd doar ce li se bifează: **paginile** (Contoare + hartă + grafice; Instalator) și **zona** — filiale întregi sau doar anumite orașe dintr-o filială (orașul din facturare; «fără oraș» se bifează separat). Fără nimic bifat nu văd nimic (pagina «/acces» le spune să ceară drepturi). Drepturile se păstrează în contul din colecția `users` (`access: { pages, branches, cities }`).
- Paginile de administrare (Consum nemăsurat, Integrare, Rapoarte, Dispozitive LoRaWAN, Facturare, Utilizatori) și API-urile lor sunt **doar pentru administratori** (403 altfel). Antenele de pe hartă la fel; un limitat vede antenele propriilor contoare, în detaliile contorului.
- Zona se aplică **pe server**, nu doar în ecran: lista de contoare (și dicționarele ei — nu apar numele altor filiale / orașe), detaliile, istoricul, poza, antenele unui contor și tot ecranul instalatorului (listă, QR, formular, poză, salvare) răspund 403 / «negăsit» pentru contoarele din afara zonei. Fiecare zonă are lista ei în memorie (gzip memorat), iar schimbarea zonei de către administrator se vede imediat (generația listei include zona).

## Limite și date personale

- Facturarea conține **date personale** (nume consumator, adresă). Ele ajung în browserul utilizatorilor autentificați (căutare instant) și în IndexedDB-ul lor; se șterg la „Ieșire”. Exportul CSV **nu** le include. Dă acces doar persoanelor autorizate.
- Un singur proces Node (`next start`): `gen`-ul listei e per proces; cu mai multe instanțe totul rămâne corect, dar browserul reface mai des descărcarea completă.
- `Volume_m3_Total` negativ (date eronate la unele contoare) nu intră în grafice și în sume.
